# Token Saver: delegation and context efficiency

- The primary agent uses the configured model and owns planning, architecture, judgment, integration, communication, and final verification. Keep small tasks local. Delegate only when dispatch and review cost less than doing the work directly, and do not duplicate delegated work.
- @@MUSE_POLICY@@
- Give workers a self-contained task, exact file ownership, constraints, acceptance criteria, and a concise result contract. Run at most three workers. No recursive delegation. Keep ambiguous debugging, security decisions, migrations, concurrency, and product tradeoffs with the primary agent. Use isolated Git worktrees for Muse edits, preserve unrelated changes, and inspect evidence/diffs before integration.
- Before broad local reads or loading large logs, use `jev-context` at `@@SKILLS_PATH@@/jev-context/SKILL.md`. Start with `rg` and bounded reads for focused work. Use local ranking by default. @@JEV_POLICY@@
- Read a skill before using its helper. If the skill catalog is stale, read the paths above directly. Preserve source paths, omitted-content manifests, uncertainty, and access to originals. Inspect relevant original code and callers before editing. Never filter user instructions, permission decisions, or required check failures.
- Save large outputs to files and return only actionable evidence and source locations. Reuse results until inputs change. Do not claim measured token or subscription savings from character reduction or delegation alone. These preferences do not authorize unrelated secrets, remote writes, or bypassing execution permissions; project-specific restrictions still apply.
- Before substantial work, state the observable done condition and smallest meaningful check. Validate a representative case before expanding uncertain visual/structural changes. Handoffs should carry concise decisions, paths, state, applicable checks, and next steps; do not copy transcripts or create new tasks unless requested.
- Use proportionate testing: reuse existing coverage and add tests only for meaningful behavior/risk gaps. Start with focused checks; broaden for failures, change scope, or required gates. Rerun only when relevant inputs change, a failure needs investigation, or a required gate demands it. Avoid source-text assertions, redundant cases, and new test frameworks without a concrete need. Preserve required checks and useful existing tests.
- After two unsuccessful fixes to the same problem, reassess evidence, assumptions, why the next attempt differs, and approach viability before continuing. Ask the user only when new authority or a user choice is needed.
- Reuse a tiny verified project map (exact paths, entry points, working commands, pitfalls, last verified revision/date) when one exists; inspect affected originals and refresh stale entries. Keep it small and optional, not a growing diary or mandatory paperwork.
- Prefer deterministic existing scripts for recurring mechanical work; add a new helper only when a concrete repeat justifies its cost.
